# 设计说明

## 为什么是"三处同时算"

一次上传只应该被记一次账，但"这空间算谁的"有三个互相独立的答案：属主、属组、目录树。地方志办的痛点是某个乡镇编纂组一次传几个 T，把整台服务器的空间和 inode 都吃光，其他组连 `mkdir` 都失败。只按用户限，挡不住"整个组一起传"；只按组限，挡不住"某个人把公共目录塞满"。所以每个存活 inode 同时计入三处用量，**任何一处到限都拒绝**。

## 探测先于记账

所有变更操作都走同一条路径：

1. 检查结构性前置条件（父目录存在、目标名不冲突、不把目录移进自己的子树……），失败返回 `*OpError`，**不记作配额拒绝**。
2. 用操作前的用量和当前执行限额做探测（`probe` / `byteRoom`），得到"放不下"的那一处。
3. 放得下就记账；放不下就整体不动（创建、移动、改属主），或只记下能放下的部分（写入、增长型截断）。
4. 拒绝时写入一条 `Denial`，其中带上探测用的用量、请求量、生效限额和软/硬限额快照。

先探测后记账保证了"拒绝不改状态"，也让每条拒绝记录都能自证超限：`Used + Demand > Limit`。写入被截断时 `Written > 0`，把 `Written` 加回 `Used` 后仍然超限，这正是"只写进没超的那部分"。

## 宽限期不靠定时器

宽限期是惰性判定的：记账时如果用量越过软限且没有在跑的宽限期，就记下 `deadline = now + Grace`；之后每次探测按 `now >= deadline && 用量 > 软限` 决定是否把执行限额从硬限换成软限。这样模拟时钟快进数百万小时也不需要扫全表，而且"停机期间宽限期到了"也自然成立。用量降回软限以下时清除宽限期状态（`updateGrace`）。

管理员延长宽限期时，未过期的顺延，已过期的从当前时刻重新计时（`extendGrace`），所以一次延长能立刻恢复按硬限执行，直到新的截止时间。

## 目录树与硬链接

目录树由目录编号继承：树根由 `Mkdir(..., treeID)` 标记，后代继承，嵌套树根截断继承。移动时把整个子树的用量从旧树转到新树，先探测目标树容量，放不下就整笔拒绝。

硬链接不增加用量（inode 已经计过账）。但一个 inode 只能属于一棵树，否则"这文件算哪棵树"就没有唯一答案，逐文件对账也就无从谈起。因此：

- 硬链接必须和文件在同一棵树内，跨树硬链接是**结构错误**；
- 有多个链接的文件不能跨树移动（结构错误）；
- 移动含"外部硬链接"的目录会被拒绝（结构错误），因为移走子树会让那些文件横跨两棵树。

这三条是刻意的取舍，写在 `Link` / `Move` 的文档里，压测器也会主动构造这些情况并断言它们是结构拒绝而不是配额拒绝。

## 校验分两层

- **每步**：`VerifyScan` 遍历所有存活 inode，按 inode 上记录的归属重新求和，与账户计数器、硬限、非负性比对。压测器还用自己的模型（它只知道"每步应该发生什么"）再对一遍，并逐条核对拒绝记录。
- **定期**：`VerifyState` 从根目录遍历目录树，按继承规则重新推导树归属，检查可达性、目录项与链接数一致性、每个位置真实存在。每 `CheckEvery` 步和结束时各做一次。

两层都用独立的累加路径，不复用引擎的记账逻辑，所以实现里的错误很难同时骗过两边。

## 随机负载

`math/rand` 固定种子，操作分布固定：约 20% 新建文件、4.5% mkdir、4.5% symlink、27% 写入、8% 截断、18% 删除、11% 移动、7% 硬链接、4% 跨树硬链接、3% 改属主、3% 改属组，以及少量改限额/延宽限期。时间平时每步推进 0 到宽限期/8，另有约 0.1% 的步一次跳过 1～6 个宽限期，保证过期/恢复都被覆盖。同一种子得到完全一致的结果（`TestDeterministic`）。
